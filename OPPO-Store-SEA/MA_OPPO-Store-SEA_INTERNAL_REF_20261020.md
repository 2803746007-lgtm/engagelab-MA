## 销售话术与尖锐问题应对

- 为什么不为每条旅程查一次接口？浏览、加购、订单和领券本来就在商城业务流程中产生，映射为事件与状态即可。兼容关系须随商品目录变化，才保留一次发送前查询。
- 是否完全无需客户开发？不是。客户需要SDK身份关联、业务事件与状态同步，按已有商品与订单记录适配兼容目录接口。工作量是方案估算，不是对现有系统的事实判断。
- 接第三方MA是否要用户再授权？MA作为数据处理者的职责与营销用途的同意分别判断。通常通过数据处理协议落实处理边界；是否另需同意由具体法域、用途及客户法务确认。营销推广仍须有效渠道同意，系统通知权限不能替代。
- 自建是否更合规？合规要求取决于用途、数据类型、权限和保留政策，不取决于自建还是采购。两种方案都应满足适用义务；不要承诺“采购即合规”。
- 图上的转化率可以写成承诺吗？不能。图为原方案演算假设；真实业务增量由随机对照评估，消息末次归因单独展示。
- 已经有商城自动化怎么办？盘点现有欢迎、购物车、新品与订单通知，按人群或场景去重，必要服务保留。若已有外部MA，先并行对照，双方频控不能自动互相感知。
- 为什么新品没有预热邮件？本轮以实际开售入口与浏览后帮助为主，减少临近开售时连续触达；后续确有预热信息与间隔需求时再加，不为增加轮次而补消息。

### 事件与属性设计合同

以下名称为建议映射，可按客户命名规范调整；含义、业务ID与金额口径不变。

| 中文事件 | 建议标识 | 最小业务字段 |

| 账号注册 | account_registered | user_id, source, email |
| 邮件营销订阅 | email_marketing_subscribed | user_id, source |
| 商品详情浏览 | product_viewed | product_id, model_id, category, context_type, detail_url, explanation_url |
| 购物车浏览 | cart_viewed | cart_id |
| 商品加购成功 | product_added_to_cart | cart_id, product_id, model_id, product_summary, cart_restore_url |
| 订单创建成功 | order_created | order_id, cart_id |
| 订单支付成功 | order_paid | order_id, cart_id, coupon_id, paid_amount, currency |
| 商品支付成功 | product_paid | order_id, product_id, model_id, line_paid_amount, currency |
| 新品机型订阅成功 | launch_subscribed | subscription_id, model_id, launch_at, campaign_ends_at, product_url |
| 权益领取成功 | coupon_claimed | coupon_id, expires_at, expiry_version, eligible_products_url |
| 权益核销成功 | coupon_redeemed | coupon_id, order_id |
| 自有商城订单签收 | store_order_delivered | source_order_id, source_model_id, product_type |
| 购后异常 | post_purchase_issue | source_order_id, issue_type |
| 配件支付成功 | accessory_paid | order_id, source_model_id, line_paid_amount, currency |

要求：外部系统在一次业务事务完成后先同步状态，再上报对应事件；事件ID幂等去重。订单与商品行事件都是同一原始订单的不同粒度映射，不能在实验收入中重复相加。配件支付只统计实际配件行。金额使用数字，币种分项目或分组，退款在实验净实付中扣除。

用户属性：historical_order_count、current_cart_id、cart_summary、cart_nonempty、cart_restore_url、has_pending_order、last_product_id、last_model_id、last_viewed_at、last_category、category_url、last_accessory_purpose、app_installed、app_push_id、web_subscribed、web_push_id、app_marketing_consent、web_marketing_consent、email_marketing_consent、email、timezone。这里的渠道资格是同步到MA的用户属性，不是假设条件分支可以直接选设备属性。购物车摘要与恢复链接随业务现状更新，防抖期间也不使用过时的商品清单。

订阅记录subscriptions为object array：subscription_id、model_id、active、campaign_ends_at。权益记录coupons为object array：coupon_id、status、expires_at、expiry_version。购物车商品清单cart_items为object array：product_id、model_id。按业务ID增量更新，不逐次重算历史聚合。匹配实例ID与状态须写在同一元素的条件内，不能用另一张券或另一条订阅满足。

旅程2使用MA分群计算近7天product_viewed次数≥2；这是用户整体商品浏览次数，不假设MA可以按任意SKU进行历史聚合。实际关注商品由本实例进入事件固定，最近商品变化则发送前结束旧轮。最近品类、最近机型与最近用途只是浏览时的覆盖值，不要求客户建设兴趣模型。

旅程2消息按context_type选择规格对比说明或商品选购说明；这只是模板变量内容，不增加隐藏的控制流。商品名、图片和链接使用本轮事件或最近值属性，默认值只用于缺失的展示内容，不用来绕过发送资格。

### 唯一Webhook

建议POST /ma/compatible-accessories。请求：user_id, source_order_id, source_model_id, last_accessory_purpose。可以封装现有商品目录、订单与售后记录；不是新增推荐模型。

响应必须为JSON对象，例如字段data.eligible、data.after_sales_ok、data.catalog_url、data.charging_name、data.charging_url、data.audio_name、data.audio_url。这里是字段合同，不是伪造的接口响应。推荐前排除已购、购物车内与待付商品。eligible与after_sales_ok必须为真且catalog_url有效；其余结束。purpose为充电且charging_url有值走充电说明，为音频且audio_url有值走音频说明，其余走兼容目录。失败、非JSON或字段缺失不发送。

### 实验与统计

1. 在客户系统按稳定用户ID随机分组，10–20%对照组在进入条件排除。抽样和分组在首条干预前完成，MA不承担A/B随机分流。
2. 对照组保留实际原有策略；实验组替代对应营销流程，必要订单与账户服务保持一致。不同市场、币种、商品范围分层。
3. 首购和商品考虑观察入组后7天；购物车以加购满1小时且仍未下单的共同资格时刻起3天；新品观察开售后7天；权益从共同资格入组至实际截止；配件从签收满7天且资格满足起14天。
4. 配件实验应先对两组用相同查询标准确认资格再锁定实验样本，不能只剔除实验组不兼容、已购或售后用户。兼容商品范围事先确定。
5. 发生跨旅程交接时，观察窗内沿用上游实验分组，购物车承接对新品两组一致，不再参加购物车实验，避免把下游重复干预算作独立增量。
6. 统计全部随机入组用户，不只统计送达或点击用户。主指标是限定范围支付率与人均净实付，过程指标分别用加购、核销及商品浏览。
7. MA消息转化率以发送数为分母；点击、打开等按组件清单2.6的分母。客户实验支付率以共同随机入组人数为分母，不能直接比较两种比率。

## 本轮局部优化：主渠道、业务判断与接入成本

本轮仅修改六条旅程、总览渠道及渠道角色表两处用途文字，不改图表、页面结构、样式、来源和排期。不新增业务事件、属性、接口或产品组件，Webhook仍为1个。

| 旅程 | 主渠道与兜底 | 节点取舍及理由 |
|---|---|---|
| 1 首购 | Email单渠道 | 邮件同意后检查首购状态，再按现有最近品类属性区分品类入口与商城目录；保留账户服务及后续订阅承接。移除不必要的App分支。 |
| 2 型号考虑 | App Push主、Email兜底 | 安装状态只决定渠道；后续明确是否仍关注本商品且未加购。说明链接已随事件携带，直接填入消息，未为规格与介绍增加两套相同结构分支。 |
| 3 购物车 | Web Push主、Email兜底 | 先判断购物车是否有效且未下单。Web路径在再次浏览后补邮件；Email首次已包含清单与帮助，发完结束。用路径表达差异，无需新增首发渠道属性。选择Web不代表已掌握客户Web流量占比。 |
| 4 新品 | App Push主、Email兜底 | 首个条件分支只按安装状态；各路径检查订阅仍有效、活动未截止及尚未加购。真实共同下游才汇合，保留48小时加购观察和再次浏览后帮助。 |
| 5 权益 | App Push主、Email兜底 | 明确判断权益仍有效、未核销及尚未加购/下单；同一判断节点承接多个必要条件，不机械拆成三个重复检查。仍只发一次。 |
| 6 购后 | Email单渠道 | 新增发送前邮件同意检查，减少无效接口调用。已购配件与售后检查继续由唯一兼容查询返回，不为提前排除新增状态同步或第二次查询。 |
